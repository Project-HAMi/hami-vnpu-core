# 调度策略选择

[English](scheduling-policies.md) · [配置参考](configuration.zh-CN.md)

通过 `NPU_SCHED_POLICY` 选择 `dynamic`、`fixed`、`overdraft` 或 `spatial`。四种策略都保留共享 HBM 计量，区别在于如何控制算力。`NPU_COMPUTE_LIMIT` 必须是 `1` 到 `100` 的整数，具体含义由策略决定。

core 库默认采用 `dynamic`，`NPU_COMPUTE_LIMIT` 默认是 `1`。部署时建议显式配置两项。core 直接从每个参与控制的应用进程环境中读取这些设置。

## 四种策略对比

| 策略 | `NPU_COMPUTE_LIMIT` 的含义 | 优点 | 取舍 | 适合的起点 |
| --- | --- | --- | --- | --- |
| `dynamic` | 时间调度中的相对份额 | 随竞争负载调整，活跃负载可以利用空闲算力 | 提交等待会产生停顿，配置值不是绝对百分比上限 | 更关注利用率、无需固定上限的共享负载 |
| `fixed` | 运行/休息比例的目标百分比 | 即使没有其他负载，也保留主动休息时段 | 休息时会留下空闲算力，提交和计时粒度影响精度与延迟 | 需要运行/休息目标且接受调度停顿的负载 |
| `overdraft` | Dynamic 份额，加上本组处于 `IDLE` 时的额外提交许可 | 正常轮次之间，等待中的提交也有机会继续推进 | 借用任务可能与其他组同时执行，算力份额更难预测 | 能接受弹性干扰的突发负载或提交敏感负载 |
| `spatial` | 用于计算每进程 Cube、Vector 核数预算的百分比 | 配合资源预算的算子可并行运行，无需等待库的时间准入 | 算子必须遵守 CANN 资源预算；预算按进程生效，不是独占物理核分区 | 希望并发执行、算子支持资源预算的负载 |

这些控制不会保证某个 tokens/s、利用率读数、延迟或优先级顺序。算子组合、内存带宽、Host 提交、算子实现以及其他设备使用者都会影响结果。应使用实际应用及预期并发方式比较各策略。

## `dynamic`：相对时间份额

参与调度的本地 SHM 组共享全局轮转。每个组在自己的轮次获得一个共享的算子准入令牌池，Manager 根据配置份额和观测到的算子时间计算令牌数量。使用同一份本地 SHM 的进程消耗同一个正常令牌池。

三个持续活跃的组分别配置 `10`、`30`、`60` 时，表达的是 `1:3:6` 的相对调度份额，不保证每个组在任意时刻都低于整卡的 10%、30%、60%。只有一个组活跃时，它可以使用超过配置比例的算力。各值无须相加等于 `100`，但每项都必须在 `1..100` 范围内。

将所有权重同时按比例放大，预期份额比例不变，但准入批次大小也会改变，因此实际调度行为不一定相同。对需要比较的负载，建议使用一致的数值尺度。

时间调度控制的是被拦截的提交入口，不会抢占已经运行的算子。因此，长算子以及不同的提交路径会影响份额精度和其他组的等待时间。

## `fixed`：运行/休息目标

`fixed` 使用相同的时间准入机制，并根据请求百分比增加休息间隔。配置 `30` 时，预期运行/休息比例约为 `30:70`；配置 `100` 时，不额外增加 Fixed 策略的休息间隔。Manager 仍然测量批次并参与全局轮转。

即使没有竞争组，该策略也保留主动休息行为。当“用满所有空闲算力”不符合限制目的时，可以选择它。配置值是调度目标，不是硬件利用率读数或精确吞吐上限；算子时长、时间估计和其他轮次都会影响实际结果。

## `overdraft`：正常轮次之间的弹性推进

`overdraft` 保留正常 Dynamic 轮转，在本组处于 `IDLE` 时增加共享准入令牌。这里的 `IDLE` 是调度器状态，不代表整张 NPU 空闲。因此，借用可能使本组与另一个组的正常轮次并行执行。

内部默认值为：令牌池容量 `10`、每次准入调用累计阻塞阈值 `5000` µs、定时等待轮询间隔 `1000` µs。阻塞时间包括该次调用进入 `IDLE` 前的等待。一次借用成功后立即返回，下一次准入调用重新累计等待时间。这些值是内部策略参数，不是环境变量。

令牌池开放且耗尽后，达到等待阈值的调用可以再次填充令牌池，同一调度轮内允许多次填充。容量 `10` 限制的是池中同时可用的令牌数，不是每轮累计借用次数、算子运行时长或未完成任务数量。需要额外推进、且能接受隔离程度更难预测时适合采用该策略；需要主动保留不借用时段时选择 `fixed`。

## `spatial`：协作式核数预算

对于每个进程、每张设备，库分别计算 Cube 与 Vector 预算：

```text
预算 = ceil(物理核数 * NPU_COMPUTE_LIMIT / 100)
```

所有有效百分比都向上取整，不设置取整误差拒绝阈值。对于 20 Cube、40 Vector 的设备：

| 配置值 | Cube 预算 | Vector 预算 |
| --- | ---: | ---: |
| `1` | 1 | 1 |
| `10` | 2 | 4 |
| `30` | 6 | 12 |
| `31` | 7 | 13 |
| `33` | 7 | 14 |
| `60` | 12 | 24 |
| `100` | 20 | 40 |

在 `aclrtSetDevice` 或 `aclrtSetCurrentContext` 成功后，库通过 CANN 设备资源 API 设置预算并读回校验。应先选择设备或 Context，再初始化算子和计算 Tiling。仅调用 `aclrtCreateContext` 不会应用预算；之后在分配/提交入口补做检查，也无法改变已经完成 Tiling 的算子。

Spatial worker 跳过正常准入令牌、时间测量、Overdraft 和全局算力轮转。本地 Manager 继续维护共享 HBM 计量和进程清理。

使用预算时需要理解以下几点：

- 每个进程在每张已初始化设备上分别获得配置预算。上述硬件上，同一组的两个 worker 进程都配置 `30`，则各自获得 6 Cube / 12 Vector，而不是共同分配一份 6/12 预算。
- 不会独占预留具体核 ID。20/40 硬件上，三个 `33` 进程的预算之和为 21 Cube / 42 Vector，实际资源由 CANN 共享；不会因为向上取整而拒绝请求。
- 算子必须查询并遵守资源预算。直接使用完整物理核数进行 Tiling 的自定义算子可能不受约束。关键算子应通过设备 Trace 确认，不能只根据预算读回成功作判断。
- 父进程开始设备初始化后，worker 应通过 spawn 或重新执行程序启动。此时 fork 出来的子进程继续使用 NPU 会被拒绝。
- CANN 运行时必须提供被拦截的设备与 Stream 资源 API。缺少 API、初始资源数无效、预算设置或读回失败时，进程以状态码 `78` 退出。同一进程初始化多张设备后，对非默认 Stream 修改资源限制会被拒绝，因为无法安全确认 Stream 的设备归属。

图执行、跨设备 Stream 使用，以及直接通过更底层接口修改资源的场景，需要单独验证应用。API 约定和实现细节参见 [Spatial 设计](spatial-policy.md)。

## 进程、组与设备的作用范围

对于 core 库，共享 `NPU_LOCAL_SHM_PATH` 的进程构成一个资源计量组。所有参与进程必须加载该库、使用相同资源配置和策略，并处于同一个 PID namespace，能互相读取 `/proc/<pid>/stat`。一个组可以由单个应用或相关 worker 进程组成，其边界由这些共享资源决定，而非部署标签。源码中也将这个组称为 Pod。

| 资源 | `dynamic`、`fixed`、`overdraft` | `spatial` |
| --- | --- | --- |
| 正常算力配额 | 本地 SHM 组内的进程共享准入令牌池 | 每进程、每设备各有一份预算 |
| 额外借用 | 仅 `overdraft` 增加 IDLE 令牌 | 无；按 CANN 资源预算执行 |
| HBM 上限 | 本地 SHM 组内的进程、设备合计共享 | 相同的共享 HBM 上限 |

`NPU_MEMORY_LIMIT_MB=20480` 表示整个组共有 20 GiB HBM 配额，不是每进程或每张选中卡各有 20 GiB。显存控制与算力策略独立。算力配置为 `100` 时仍保留显存控制以及所选策略的 Hook，并不会移除库。

时间调度负载只会与共享其全局注册表的参与者协调。Spatial 负载和未加载 Hook 的应用不加入时间轮转。混合部署需要规划容量：时间调度组的百分比不会限制相邻负载。

## 配置与策略切换

准备好共享文件和库后，显式配置一个参与负载：

```bash
export NPU_GLOBAL_SHM_PATH=/hami-shared-region/device-7-registry
export NPU_LOCAL_SHM_PATH=/tmp/vnpu-local
export NPU_MEMORY_LIMIT_MB=20480
export NPU_COMPUTE_LIMIT=30
export NPU_SCHED_POLICY=spatial
LD_PRELOAD=/opt/hami/libvnpu.so python3 your_model.py
```

以上路径仅为示例：需要协调的负载，其全局路径必须指向同一份共享文件；本地文件只在本组的参与进程之间共享。注册表文件名不会选择应用使用的设备。默认值、单位、日志和旧变量迁移方式参见 [配置参考](configuration.zh-CN.md)。

改用 `NPU_SCHED_POLICY=dynamic`、`fixed` 或 `overdraft` 即可选择其他策略。比较三个负载时，分别使用三份本地 SHM，算力值可以设为 `33/33/33` 或 `10/30/60`。对于 Dynamic、Overdraft，它们是相对份额；对于 Fixed，它们是各自的运行/休息目标；对于 Spatial，它们生成独立向上取整的每进程核数预算。

配置在进程/Manager 初始化时读取，不会实时监听变化。切换策略、百分比或共享内存布局时，应停止共享该本地 SHM 的全部进程，部署一致的库版本和配置，再使用新的本地 SHM 文件重启。不要混用新旧进程，也不要移除正在使用的 SHM 文件。其他协调负载仍使用全局注册表时，应保留该文件；如果升级修改了其布局，需要协调停止全部使用者。
